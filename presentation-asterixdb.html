01 · The problem

Spatial joins need more than an equality key

Nested loop

Broadcast one input and test pairs. Useful for small inputs, but expensive when both grow.

Bounding boxes

Cheaper than exact geometry predicates, but a filter alone still considers the pairs.

Index lookup

Useful for selective inputs; repeated probes can become expensive for larger joins.

Goal: reduce candidate pairs and distribute work inside a composable SQL++ query plan.

02 · My contribution

An optimizer-visible spatial join

Planning

Added optimizer rewrites, a spatial partitioning hint, and a physical operator specifying partitioning and ordering.

Execution

Added a partition-based spatial merge (PBSM) plan and a local plane-sweep runtime.

Minimum bounding rectangles (MBRs) filter candidates. The original spatial predicate remains for exact refinement.

03 · Query and planning

From a predicate to a physical plan

SELECT COUNT(*) FROM ParkSet AS ps, LakeSet AS ls
WHERE /*+ spatial-partitioning(-180.0, -83.0, 180.0, 90.0, 10, 10) */
  st_intersects(ps.geom, ls.geom);

Optimizer

Recognizes an eligible inner join, introduces MBR overlap, and keeps st_intersects.

Physical operator

Selects SPATIAL_JOIN and requires both inputs to be partitioned and ordered.

The hint specifies bounds and a 10-by-10 grid. Eligible unhinted joins can compute bounds dynamically and use a default grid.

04 · Distributed execution

From grid to exact matches

01

Find the grid

Use hinted bounds or compute and intersect the inputs' bounds.

02

Tile & shuffle

Replicate MBRs across overlapping tiles; partition both sides by tile ID.

03

Sort & sweep

Order by tile and rectangle, then generate candidates locally.

04

Refine

Use a reference tile to avoid duplicates and apply the exact predicate.

The dynamic path computes grid information within the query plan and materializes an input branch for reuse.

05 · Inside the plane sweep

Ordered rectangles narrow the candidate search

Local processing

  • Write the sorted build input to a run file.
  • Advance through ordered streams and buffer potentially overlapping probe rectangles.
  • Check overlap in both dimensions before emitting a candidate.

Bounded memory

When the probe buffer fills, the joiner processes buffered tuples against the remaining build run, clears the buffer, and rewinds the build stream.

Sorting, run-file I/O, buffering, and possible rereads are part of the cost.

06 · Correctness

One pair, one reference tile

Prevent duplicate pairs

For overlapping MBRs A and B, use the lower-left corner of their intersection:

x = max(A.minX, B.minX)
y = max(A.minY, B.minY)

Retain the pair only in the tile containing this reference point.

Preserve matches

Assign each rectangle to every overlapping tile. MBR overlap is conservative, so the exact geometry predicate must still be checked.

For supported distance comparisons, expand one MBR by the threshold before filtering.

Grid hints must cover the region containing the matches of interest.

07 · Performance tradeoffs

Grid size trades local work for replication

Too coarse

Large cells increase local candidate work and can leave workers unevenly loaded.

Too fine

More cells can increase replication, shuffle, and sorting, especially for large geometries.

Skew

Dense regions can create hot tiles and stragglers even when total work appears balanced.

A uniform grid is not a universal solution: both very small and very large grid sizes can perform poorly.

09 · Experiment 1: AsterixDB plans

Compare the same query with and without the rewrite

Input & setup

5,000 rectangles and 250,000 points; 1.25 billion possible pairs. Same files, query, build, and cluster settings.

Two local nodes, compiler parallelism 4, and a hinted 100-by-100 grid for the optimized plan.

Two plans

Baseline: NESTED_LOOP, with the geometry rewrite disabled in an isolated optimizer class.

Optimized: SPATIAL_JOIN. Both returned 124,687 matches, confirmed independently.

This is a same-build counterfactual, not a benchmark of a historical pre-contribution binary.

10 · Experiment 1: results

151.056 s → 0.380 s median

About 398× faster on this input: three measured baseline queries versus six optimized queries across two batches.

11 · Experiment 2: AsterixDB and Sedona

Same data, different execution systems

AsterixDB

Two local nodes, Java 21, parallelism 4, a fixed 100-by-100 grid, local plane sweep.

Sedona

Spark 3.5.0 on Java 11, local[4], eight join partitions, KDB-tree partitioning and local R-trees. Broadcast and experimental plane sweep disabled.

Both read identical JSON/WKT files. Times include parsing, partitioning, sorting or index construction, exact refinement, and result retrieval; startup and dataset/view setup are excluded.

14 · Interpretation

What might explain the results?

Partitioning

The fixed AsterixDB grid avoids deriving a partitioner; Sedona analyzes the dominant input and builds a KDB-tree partitioner.

Local work

Plane-sweep sorting and run-file work differ from R-tree construction and probing. Replication and candidate counts may differ too.

Overheads

Scheduling, JVMs, memory settings, warm-up, and data distribution can affect end-to-end times.

These are hypotheses: the experiments did not measure per-stage costs or isolate plane sweep from the rest of each engine.

15 · Algorithm selection

When might another plan win?

Choose another approach

  • Broadcast nested loop for an input that fits efficiently in memory.
  • Index lookup for a highly selective input with a suitable index.
  • Avoid a costly grid when replication, shuffle, or skew dominates.

Keep semantics safe

Unsupported predicate shapes or filters that cannot preserve semantics require another valid plan.

Actual alternatives depend on the query and implementation.
