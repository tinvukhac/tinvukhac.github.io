How I implemented spatial join in AsterixDB

I implemented a distributed partition-based spatial merge (PBSM) join and integrated it end-to-end into AsterixDB's optimizer and Hyracks execution engine, rather than adding only a standalone geometry algorithm.

This walkthrough follows commit 4f1090d, [ASTERIXDB-2839] Added Optimized Spatial Joins. It describes the logical implementation flow, not the chronological order in which the files were written. For experiments and measured performance, see the project page's local experiments.

The short explanation

I implemented Partition-Based Spatial-Merge Join, or PBSM, in AsterixDB. The idea is to avoid comparing every object from one dataset with every object from the other.

I added optimizer rules that recognize supported spatial predicates and transform them into a filter-and-refine plan. We first use minimum bounding rectangles to generate candidates cheaply, then evaluate the original geometry predicate for accuracy.

For distributed execution, I partitioned the spatial domain into grid cells, replicated each object into the cells its bounding rectangle overlaps, and redistributed both inputs by cell ID. Within each worker, I used a sorted plane-sweep join to reduce local comparisons.

Replication can produce the same pair in multiple cells, so I added a reference-point ownership rule to emit each pair only once. I also implemented bounded-memory execution using a disk-backed run file, supported automatic or user-specified partitioning, and added optimizer-plan and runtime regression tests.

Step-by-step implementation

1. Teach the optimizer to recognize spatial joins

I connected spatial-join selection to AsterixJoinUtils and added rewrite rules to the optimizer's rule collections. The implementation supports rectangle intersection directly and introduces filter/refine rewrites for geometry predicates such as:

st_intersects(a.geom, b.geom)
st_contains(a.geom, b.geom)
st_within(a.geom, b.geom)

I also extended function extraction so expressions used by the rectangle-intersection predicate can become variables available on the appropriate input branches.

The first part was compiler integration: recognize eligible spatial joins and construct a specialized physical plan instead of treating the predicate as an arbitrary function.

Implementation: AsterixJoinUtils, RuleCollections, and AsterixExtractFunctionsFromJoinConditionRule.

2. Separate cheap candidate filtering from exact geometry evaluation

For a predicate such as st_intersects(a.geom, b.geom), the rewrite adds a necessary bounding-box condition. Conceptually:

spatial_intersect(MBR(a.geom), MBR(b.geom))
AND st_intersects(a.geom, b.geom)

The rectangle test generates candidates; the original function remains responsible for the exact answer. Overlapping bounding boxes alone do not prove that two complex geometries intersect.

For supported distance comparisons such as:

st_distance(a.geom, b.geom) <= d

where d is constant, I enlarge one geometry's MBR by d, intersect it with the other MBR, and retain the original distance comparison as refinement. The rule recognizes <, <=, and = in that expression shape.

Implementation: FilterRefineSpatialJoinRuleForSTFunctions and FilterRefineSpatialJoinRuleForSTDistanceFunction.

3. Establish a shared grid for both datasets

Both inputs must use the same spatial partitioning scheme. I implemented two paths:

PathHow the grid is established
StaticA spatial-partitioning(minX, minY, maxX, maxY, rows, columns) hint supplies the bounds and grid dimensions. The bounds must cover the region containing the matches of interest.
DynamicLocal/global MBR aggregates compute each input's overall bounds. Their intersection becomes the partitioning region, using a default 100-by-100 grid.

The dynamic path replicates each input into an aggregation branch and a materialized data branch. Once the common bounds are available, the data can proceed using those bounds. The small spatial summary is broadcast, not both complete datasets.

I supported automatic partitioning, but also exposed a hint so users who know their data can avoid the dynamic-summary overhead and tune the grid.

Implementation: SpatialJoinUtils.

4. Replicate objects into overlapping cells and redistribute them

I introduced the spatial-tile unnesting function. For each rectangle, it emits the IDs of the grid cells it overlaps. Conceptually:

Object A overlaps cells 7 and 8
    → (7, A)
    → (8, A)

Replicating boundary-crossing objects is necessary: assigning an object to only one cell could miss matches in another cell.

Both inputs are then hash-partitioned by tile ID, bringing corresponding cells together. A worker can process multiple cells; a grid cell is not the same thing as a machine.

Implementation: SpatialTileDescriptor.

5. Declare ordering requirements and execute a local plane sweep

SpatialJoinPOperator declares that both inputs must be partitioned by tile ID and sorted by tile ID, then rectangle order, which begins with the rectangle's minimum X coordinate.

AsterixDB's physical-property machinery supplies the necessary exchanges and sorts. The runtime operator then processes matching tiles using a plane sweep.

Conceptually, it advances through X-ordered rectangles, retains potentially relevant probe rectangles, removes rectangles that can no longer match, and stops scanning candidates when later rectangles are too far to the right. Surviving pairs receive the rectangle-overlap test, including Y overlap.

The grid reduces comparisons globally, and the plane sweep reduces comparisons locally. They solve different parts of the problem.

Implementation: SpatialJoinPOperator, PlaneSweepJoinOperatorDescriptor, and IntersectSpatialJoinUtil.

6. Make the runtime work with bounded memory

This implementation does not assume every partition fits in RAM. The Hyracks operator has separate build and probe activities. The build activity materializes its input into a run file; the probe activity streams the other input and maintains an in-memory candidate buffer.

When that buffer fills, the implementation processes buffered candidates against the remaining relevant build stream, clears the buffer, and restores the saved build position before continuing.

I integrated the algorithm with Hyracks' frame and tuple-buffer infrastructure and used a disk-backed build stream so execution could continue under a fixed memory budget.

Implementation: SpatialJoiner.

7. Eliminate duplicates introduced by spatial replication

Two objects may overlap several shared cells, producing the same candidate pair repeatedly. I compute a deterministic reference point from their rectangles:

referenceX = max(a.minX, b.minX)
referenceY = max(a.minY, b.minY)

For intersecting rectangles, this is the lower-left corner of their intersection. The cell containing that point owns the pair; only that cell's copy is retained.

This avoids a global DISTINCT or a distributed set of previously emitted pairs. It eliminates replication-created duplicates, rather than removing legitimate duplicate input rows.

Implementation: ReferenceTileDescriptor.

8. Apply refinement and validate the integration

PullSelectOutOfSpatialJoin moves predicates other than the rectangle-intersection condition into a selection above the specialized join. That preserves the original exact geometry predicate and other conditions while keeping the local operator specialized.

I added expected optimizer plans showing the unnest → hash exchange → sort → spatial join pipeline, plus runtime cases for static partitioning, dynamic partitioning, hints, and a left-outer-join regression case. The latter is not evidence that the new PBSM path optimizes outer joins; the filter/refine rewrite rules explicitly target inner joins.

Implementation: PullSelectOutOfSpatialJoin, optimizer-plan tests, and runtime tests.

The complete execution flow

SQL++ spatial join
    → recognize predicate and add MBR filter
    → establish shared grid bounds
    → emit one tuple per overlapping tile
    → redistribute both inputs by tile ID
    → sort locally by tile ID and rectangle order
    → plane-sweep rectangle join
    → reference-tile duplicate elimination
      and exact-predicate refinement
    → query result

The precise placement of duplicate elimination differs between the static and dynamic plans.

Design questions and limitations

Is this an R-tree join?

No. This commit implements grid-partitioned PBSM with a local plane sweep, without requiring a prebuilt spatial index.

Is it always faster or always O(n log n)?

No. It reduces unnecessary comparisons when partitioning and spatial selectivity are favorable. Sorting, redistribution, replication, dynamic materialization, skew, and large overlapping objects all affect performance. Dense overlap can still produce quadratic candidate work or output.

Was the hint required?

Not in the committed implementation. Although the commit message says it was, the code and no-hint runtime test implement the dynamic path.

What was the main engineering contribution?

I took a spatial-join algorithm and made it a native distributed database feature: predicate rewrites, physical planning, partitioning and ordering requirements, memory-aware execution, duplicate handling, and regression coverage.
