R-Grove: spatial partitioning for distributed data

Adapting R-tree ideas to organize large spatial datasets across machines.

Tin Vu

Use the arrow keys or the controls below to navigate.

01 · The problem

A good local index is not automatically a good distributed partitioner

Load balance

Uneven partitions create unequal work and slow distributed jobs.

Spatial quality

Partition shapes and overlap affect how much data a spatial query must examine.

Coverage

Boundaries based only on a sample must still handle records not represented by that sample.

Treating an R-tree built on a sample as a black box can leave gaps or produce poorly balanced partitions.

02 · My contribution

Grow a family of distributed spatial indexes

Grove family

I developed R-Grove, R*-Grove, and RR*-Grove, adapting the main ideas of their R-tree counterparts to big spatial data.

System integration

The methods are available in Beast, a distributed geospatial processing system built on Apache Spark.

The goal is spatially useful partitions for distributed processing, rather than a record-level search tree on one machine.

03 · How it works

Use samples to build boundaries, then partition the data

01

Sample

Draw a manageable sample of the input dataset.

02

Split

Apply adapted R-tree splitting to form balanced spatial partitions.

03

Track boundaries

R*-Grove and RR*-Grove can use split history to define disjoint regions.

04

Distribute

Assign the full dataset to the resulting spatial partitions for processing.

For R*-Grove and RR*-Grove, split history maintains coverage and disjoint partition regions; geometries crossing boundaries can still be replicated.

04 · Design tradeoffs

Balance partition size with spatial shape

Balance

R*-Grove uses a balance factor to limit differences in partition sizes.

Shape

R*-tree-inspired splits aim for spatially useful regions, not merely equal record counts.

Record size

A sample can be combined with a storage-size histogram to account for records with different sizes.

The best balance depends on the data and workload: equal-sized partitions alone do not guarantee low query cost.

05 · Evaluation

Measure both partition quality and query performance

Partition behavior

The research examines the effects of spatial distribution and partitioning choices on the resulting partitions.

Downstream work

Experiments on large spatial datasets evaluate partition quality and query performance; the papers describe the datasets and comparisons.

Results are workload-specific; no single partitioner is assumed to be best for all distributions.

06 · Further directions

Choosing and maintaining partitions remains a systems problem

Representativeness

Study how sample size affects the resulting boundaries on skewed data.

Workloads

Compare partition choices across range queries, joins, and changing workloads.

Change over time

Explore when evolving data calls for incremental reorganization.

These are possible directions, not claims about the existing implementation.
